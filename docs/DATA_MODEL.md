# FORGE Data Model & Exercise Library Reference

**Purpose:** Single source of truth for how exercise/program data is stored and
which store is authoritative. (As of 2026-09-24.)

## Stores at a Glance

| Store | Location | Contents | Role |
|---|---|---|---|
| Engine data module | `src/forge/exercises_data.py` | 334 exercises (7,708 lines) | What the Python generation engine selects from at runtime |
| Conditioning data | `src/forge/conditioning_data.py` | Conditioning protocols | Energy-system work selection |
| Frontend seed JSON | `forge_web/src/data/exercises.json` / `complexes.json` | 537 exercises / 222 complexes | Offline-first library browsing in the coach console |
| UI taxonomy | `forge_web/src/data/exerciseOrganization.ts` | 7 super-categories over ~22 categories | Library navigation grouping |
| SQL migrations | `migrations/0000NN_*.sql` (through `000035`) | Schema + seeded library phases | Canonical relational model (`exercises`, `exercise_tags`, `exercise_movement_patterns`, `exercise_equipment`, `exercise_sport_mapping`, `exercise_physical_qualities`, `exercise_training_methods`, …) |
| Local database | `forge.db` (SQLite) | Applied migrations | Runtime persistence for programs/athletes |

**Authority rule:** the SQL migrations define the canonical schema; the engine
module and frontend JSON are generated/maintained views. When counts disagree,
the migration set wins and the views must be re-synced (see `MIGRATIONS.md`).

## Known Duplication Risk

The three views are maintained by separate one-off scripts in the repo root
(`add_exercises*.py`, `enrich_*`, `integrate_phase*.py`, `dump_exercises.py`).
Adding an exercise to only one view causes drift (historically: 271 vs 334 vs
537). Always update via migration first, then regenerate JSON/engine data.

## Exercise Record — Key Fields

Frontend records (`exercises.json`) carry coaching metadata added in
migrations 000026+:

| Field | Type | Notes |
|---|---|---|
| `id` / `name` | int / string | IDs allocated per migration phase; keep globally unique |
| `category` | string | Maps into a super-category in `exerciseOrganization.ts` |
| `movement_pattern` | enum | E.g., hinge, squat, push, pull, carry, unilateral hip dominant |
| `equipment` | list | Tags table `exercise_equipment` |
| `primary_muscles` / secondary | list | Via `000006_add_muscles_schema` |
| `coaching_cues` | list(4) | Required for CSCS-grade entries |
| `common_faults` | list(4) | Required |
| `contraindications` / pain-safe flags | list | Phase 7 bridge & pain-safe expansion |
| `development_level` | enum | Olympic-lift levels fixed in `000019` |
| `technical_difficulty` | numeric | Populated in `000020` |
| `sport_mapping` | list | `exercise_sport_mapping`; cricket/badminton seeds in `examples/`, `badminton_audit_v2/` |
| `progression_chain` / `regression` | refs | Built by `build_progression_chains.py` |

Complexes (`complexes.json`, 222 entries) compose ordered exercise lists with
transition/rest rules; generated by `generate_complexes.py`, repaired by
`fix_complexes.py`.

## Validation

Run `python validate_library.py` (schema/completeness checks) before merging
any library change; see `TESTING.md` for related suites.
